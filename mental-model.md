# Mental Model — Uptime Kuma

> مسیر یادگیری: Mental Model Code Discovery | نسخه: 2.5.3 | Node >= 20.4
> سبک سند: ساده، خودمانی و بدون تکلف مهندسی

---

## STEP 0: پروژه درباره خودش چه می‌گوید؟

### هدف اصلی
ابزار **مانیتورینگ شخصی و سبک (Self-hosted)** جایگزین سرویس‌های ابری مثل Uptime Robot.

### زبان کسب‌وکار (Ubiquitous Language)
- **Monitor:** هدف تحت پایش (وب‌سایت، پورت، دیتابیس و...).
- **Heartbeat:** نتیجه‌ی یک بار سنجش وضعیت (پاسخ/خطا، زمان پاسخ، تاریخ).
- **Status Page:** ویترین عمومی برای نمایش آنلاین بودن سرویس‌ها به دیگران.
- **Notification Provider:** پل‌های ارتباطی هشدار (تلگرام، ایمیل، دیسکورد و ۹۰+ مورد دیگر).

---

## STEP 1: ساختار و نقشه راه کدهای پروژه

### نقطه شروع (Entry Points)
- **بک‌اند:** `server/server.js` (موتور محرک کل سیستم، مدیریت دیتابیس، زمان‌بندی و پورت ۳۰۰۱).
- **فرانت‌اند:** `src/main.js` (رابط کاربری Vue 3 که در بیلد نهایی در پوشه `dist` می‌نشیند و خود سرور آن را سرو می‌کند).

### تقسیم کار پوشه‌ها
- `server/model/`: تعریف موجودیت‌های هسته (`monitor.js`, `heartbeat.js`).
- `server/monitor-types/`: الگوریتم‌های ۲۷ نوع سنجش مختلف (`http.js`, `ping.js`, `dns.js`...).
- `server/notification-providers/`: تنظیمات ارسال هشدارها.
- `server/socket-handlers/`: کانال‌های مکالمه دوطرفه با رابط کاربری.
- `src/pages/` و `src/components/`: ظاهر گرافیکی برنامه.
- `db/`: مهاجرت‌ها و ساختار پایگاه داده.

```text
[۱. کاربر در UI] ─── socket.emit("add") ───► [۲. سرور (server.js)]
                                                      │
                                             اعتبارسنجی و ذخیره مانیتور
                                                      │
                                                      ▼
                                             [۳. دیتابیس SQLite]
                                                      │
                                                      ▼
                                           [۴. چرخه سنجش beat()]
                                            اجرای منظم (مثلاً هر ۲۰ ثانیه)
                                                      │
                                                      ▼
                                           [۵. ثبت نتیجه: Heartbeat]
                                                      │
                     ┌────────────────────────────────┴────────────────────────────────┐
                     ▼                                                                 ▼
          [۶. آپدیت بدون رفرش UI]                                            [۷. هشدار هوشمند]
       io.emit("heartbeat")                                          اگر خطا تکرار شد (اتمام Retries)
       (تغییر رنگ به سبز/قرمز)                                         ارسال به تلگرام/ایمیل
```

## STEP 3: مستندسازی مدل ذهنی و دلایل تصمیم‌گیری (Architectural Decisions)

### ۲. چرا این شکلی ساخته شده؟ (Architecture Decision Records - ADR)

| تصمیم معماری | چرا این انتخاب شد؟ | اگر راه سنتی/پیچیده‌تر می‌رفت چه می‌شد؟ |
| :--- | :--- | :--- |
| **WebSocket به‌جای REST API** | برنامه مانیتورینگ نیازمند نمایش زنده و لحظه‌ای ثانیه‌ها و تپش‌هاست. | اگر REST بود، مرورگر باید هر ثانیه صدها درخواست Polling بی‌مورد به سرور می‌زد که باعث افت شدید عملکرد می‌شد. |
| **SQLite توکار به‌جای دیتابیس جدا (Postgres/MySQL)** | راحتی کاربر معمولی در اجرای برنامه؛ کاربر فقط با اجرای یک خط داکر بدون درگیر شدن با نصب سرور دیتابیس، برنامه‌اش بالا می‌آید. | نیاز به دیتابیس جداگانه باعث پیچیده شدن نصب (نیاز به docker-compose چند کانتینری و رم بیشتر) برای مصارف خانگی می‌شد. |
| **تک‌پروسه بودن (Monolith) فرانت و بک** | سادگی در استقرار؛ فرانت فقط یک پوشه استاتیک داخل بک‌اند است. | جدا کردن فرانت و بک‌اند نیاز به تنظیمات Nginx، مدیریت CORS و کانفیگ‌های شبکه اضافه داشت. |
| **زمان‌بندی داخلی درون حافظه (In-Memory Scheduler)** | عدم نیاز به ابزارهای پیچیده مثل Redis یا Celery/RabbitMQ برای صف کارهای زمان‌بندی‌شده. | برای یک ابزار self-hosted استفاده از Redis فقط بار مصرف رم سرور کاربر را بی‌جهت بالا می‌برد. |

### ۳. محدودیت‌ها و سقف مقیاس‌پذیری این مدل ذهنی (Trade-offs)
- **مزیت:** مصرف بسیار پایین منابع (زیر ۱۰۰ مگابایت رم)، نصب فوق‌ساده با یک فایل یا ایمیج، سرعت پاسخ‌دهی بالا.
- **نقطه ضعف / Ceiling:** چون همه‌چیز داخل یک پروسه نود اجرا می‌شود، توان بررسی هم‌زمان حداکثر چند صد تا چند هزار مانیتور را دارد. برای مانیتورینگ در مقیاس‌های انترپرایز ده‌ها هزار تارگت، تک‌پروسه نود به گلوگاه می‌خورد.
